# Контракт страницы (schema)

Правила формата и именования страниц `wiki/`. Этот файл копируется в корень каждого вики-проекта как `schema.md`. Жёсткого шаблона тела нет — каждый концепт принимает свою форму, но **инварианты 1–9 обязательны на каждом листе**.

> **Ссылки — только обычные markdown `[Имя](путь.md)`** (без Obsidian `[[ ]]`/dual-link), чтобы вику читал любой агент/редактор/человек и она оставалась рабочей даже без конкретного инструмента. **Диаграмм нет** — агенту визуал не помогает (Mermaid читается как текст-токены), структуру дают типизированные связи + «На этой странице» + списки/таблицы.

## Именование файлов

- На языке источника, нижний регистр, слова через дефис: `работа-с-возражениями.md`, `возражение-дорого.md`.
- Латиница — только для устоявшихся терминов: `crm.md`, `spin.md`, `roi.md`.
- Все страницы в `wiki/` **плоско**, без подпапок. Иерархия — через хабы и ссылки, не через папки.
- **Путь в ссылке — относительно файла.** Страницы из `wiki/` ссылаются на соседей голым именем (`voronka-prodazh.md`). `index.md` лежит в **корне проекта**, поэтому на страницы ссылается с префиксом `wiki/` (`wiki/voronka-prodazh.md`) — иначе ссылки из точки входа не резолвятся.
- **Slug стабилен** — имя-идентификатор не переименовывать (на него завязаны ссылки). Дубль → слить, вторую заменить заглушкой-перенаправлением (см. ниже).
- **Мультиязычные источники:** canonical-язык slug — по первому источнику вики; тот же концепт на другом языке → в `aliases`, не второй slug.

## Иерархия: хаб + листья

- **Единица вики = концепт**, не глава/урок. Хронология источника живёт в `sources/`, не в `wiki/`.
- **Хаб** — карта темы верхнего уровня («Работа с возражениями»). **Лист** — конкретный подконцепт («дорого», «я подумаю»).
- `index.md` — точка входа и карта. **До неск. сотен страниц — ПОЛНОЕ иерархическое оглавление:** каждый хаб = раздел с 1-строчным описанием, под ним **вложенный список всех своих листьев** (с однострочниками). Так структура видна целиком с одной страницы (иначе вика ощущается «свалкой», хотя иерархия есть в хабах). «Только карта хабов, без листьев» — лишь когда индекс реально перерос порог (см. `lint.md`, «Метрика масштаба»).
- **Инвариант связности:** каждая страница достижима из `index.md` через одну или несколько ссылок. Сирот ловит lint.
- **Гранулярность:** если про штуку можно написать ≥ полстраницы с примерами и тактикой — отдельная страница. Если нет — живёт в родителе.

## Frontmatter (YAML) — инвариант 1

```yaml
---
type: hub | concept | technique | entity | example | quote | redirect
title: <читаемое имя на языке источника>
aliases: [<синонимы для поиска>]
sources: [<файлы из sources/>]
redirect_to: <новый-slug>.md   # только для type: redirect
---
```

Обязательны всегда: `type`, `title`. `aliases` — опционально. **`sources` — по типу:** лист (`concept`/`technique`/`entity`/`example`/`quote`) — **обязателен**; `hub` и `index.md` — **не требуется** (навигационные); `redirect` — вместо него обязателен `redirect_to`.

> **`type` — обязательное поле формата OKF v0.1** (см. «Совместимость с OKF» ниже). Раньше это поле звалось `category`; имя изменено на `type`, набор значений тот же.

## Обязательные элементы листа (инварианты 2–9)

2. **H1** — совпадает с `title`.
3. **Лид-абзац** (1–3 предложения) сразу после H1, без заголовка — что это и для кого. Суть понятна, даже если дальше не читать.
4. **Блок «На этой странице»** — 3–5 вопросов, на которые лист отвечает. Это TOC для агента: видно, можно ли вытащить ответ, не читая весь лист. Достаточно списка вопросов; **ссылку на внутренний якорь раздела (`#…`) НЕ требовать** — авто-якоря ломаются при переименовании заголовка, и пустая стрелка «в никуда» хуже её отсутствия.
5. **Заголовки разделов — вопросы/действия**, не таксономия: «Как отработать» / «Чего не делать» / «Когда применять» / «Типовой скрипт». Не «Шаги», не «Детали».
6. **Вербатим-якорь** — минимум один на лист (см. правило дозы ниже). Байлайн `<источник>` — автор(ы) и заголовок из метаданных источника, единообразно по всей вике (авторов бывает несколько — «Ильяхов, Скрябин», не один зашитый):
   ```
   > «дословная цитата»
   > — <источник>, `sources/<файл>`, строки X–Y.
   ```
7. **Inline-глоссы для внешних концептов.** При первом упоминании ссылки на другую страницу — короткая расшифровка прямо в тексте, чтобы лист читался самодостаточно. Агент, вытащивший один лист, не должен «сесть» на незнакомом термине.
   - Плохо: «разрушает принципы обмена».
   - Хорошо: «разрушает принципы обмена (модель из 4 типов обмена…; продавец должен идти чуть выше клиента)».
   - *Как и типизированные связи, глоссы финализируются на стадии wikilinks (когда известен полный реестр страниц); lint проверяет инв. 7 на финальном графе, не на свежесозданной странице.*
8. **Блок «Куда идти дальше»** — типизированные ссылки (см. ниже).
9. **Блок «Источники»** в конце — полный список файлов и диапазонов строк, ушедших в страницу. Формат машинно-проверяемый, по строке на запись: `- sources/<файл>.md:12-18 — что использовано`. Так lint сверяет покрытие.

## Правило дозы вербатима

Вербатим — **слой доверия под несущим утверждением** (точная формулировка правила, название приёма, ключевой тезис автора), **а не цитата под каждым предложением**. Связующий синтез, объяснения, переходы — своими словами.

- Правило: **нельзя выдавать за слова автора то, что не процитировано.** Нет цитаты → либо явно твой синтез, либо `[заполнить позже]`; не выдуманная цитата, не приписанное автору.
- **Сильный дефолт для методичных источников** (правила, скрипты, формулы — там важна точная формулировка). На чисто концептуальном материале допустимо реже. Минимум один якорь на лист.
- Цитаты короткие (копирайт): ориентир ≤ ~40 слов, без копирования длинных пассажей.
- *Мягкая проверка lint (не блок):* текст якоря дословно (с нормализацией пробелов/кавычек) находится на указанных строках источника? Нет → предупреждение «строки не сошлись, проверь». Страхует именно номера строк (модель их считает плохо), не смысл.

## Типизированные связи (блок «Куда идти дальше»)

Каждая ссылка — с **типом отношения**, свободным текстом (жёсткий словарь не требуется). Базовые типы-ориентиры:

- **родитель-хаб** — узел темы, к которому относится лист.
- **предпосылка** — что понять до этого.
- **следующий шаг** — что идёт после.
- **противопоставление** — похожее, но другое (важно не спутать).
- **частный случай** — конкретизация общего приёма.

**Формат — только обычная markdown-ссылка:**

```
- [Имя страницы](имя-страницы.md) — <тип / как связано>
```

Без `[[ ]]`, без dual-link. Связи проставляются **отдельным проходом** (`wikilinks.md`), не по ходу письма.

## Размер страницы

Концепт-лист ориентир **≤ ~800 слов**. Если раздулся:

- покрывает **несколько концептов** → **split** (каждый — свой лист + связи + при нужде хаб);
- **один концепт, но многословно** → **shorten** (ужать синтез, вербатим-якоря оставить).

Хаб — навигационный узел, держать компактным. Lint **предупреждает** при перерастании (не режет).

## Хаб-страница и `index.md` (контракт иной, чем у листа)

Инварианты 2–9 (лид, «На этой странице», вербатим-якорь, «Источники») — **для листьев**. У хабов и `index.md` свой контракт. **Важно различать:** хаб — обычный `wiki/*.md` (non-reserved концепт-док), а `index.md` — reserved-файл OKF, и frontmatter у них **разный**.

**Хаб-страница** (`wiki/<тема>.md`):
- Frontmatter — да (`type: hub`, `title`); **`sources` и вербатим-якорь не требуются** (хаб навигационный, не несёт утверждений автора).
- Вместо «как применить» — **карта темы**.
- Секция «С чего начать» — точка входа.
- Группировка листьев по смысловым блокам (механика / разборы / примеры) с 1-строчным описанием каждого.

**`index.md`** (reserved-файл OKF — структура §6):
- **Без frontmatter.** Единственное допустимое поле — `okf_version: "0.1"` в корневом `index.md` (объявление версии формата; больше frontmatter в `index.md` OKF не разрешает). Тип/заголовок в YAML **не ставить** — это reserved-листинг, не концепт-док.
- Тело — карта-листинг для прогрессивного раскрытия. До неск. сотен страниц — **полное иерархическое оглавление** (хаб → его листья вложенным списком), а не только перечень хабов (см. раздел «Иерархия» выше и `lint.md`).

## Тип (`type`)

**Закрытый список из 7 — других не бывает** (передавать сабагентам именно так, иначе выдумывают свои):

`hub` — карта темы · `concept` — теория/модель/принцип · `technique` — приём/скрипт/формула · `entity` — человек/компания/продукт/инструмент · `example` — разбор случая/диалога · `quote` — значимая цитата с контекстом · `redirect` — заглушка после слияния дублей. Если подходит несколько — по доминанте.

В терминах OKF v0.1 это «descriptive type identifiers» (реестр там открытый — мы сознательно сужаем до 7). Развести два направления, чтобы не сломать собственный контракт:
- **На чтении** чужого OKF-бандла — **терпеть незнакомый `type`**, не падать (так велит OKF потребителю).
- **На записи** наших страниц — `type` **всегда одно из 7**. Чужой исходный тип не тащить в наш `type`; нужен — сохранить в провенансе (поле `okf_type:` или строкой в «Источники»), а наш `type` выставить маппингом по смыслу.

## Совместимость с OKF v0.1

`wiki/`-страницы вместе с `index.md`/`log.md` образуют бандл, conformant к [Open Knowledge Format v0.1](https://github.com/GoogleCloudPlatform/knowledge-catalog/blob/main/okf/SPEC.md) — формат автора и OKF растут из одной вики-идеи (atomic md + `index.md`/`log.md` + относительные ссылки + frontmatter). Conformance держится на трёх вещах, и их **нельзя ронять**:

1. **Каждая страница `wiki/*.md` — с парсимым frontmatter и непустым `type`** (единственное жёсткое требование к концепт-докам; lint проверяет).
2. **Reserved-файлы следуют своей структуре** (OKF §6/§7): `index.md` — **без frontmatter** (кроме допустимого `okf_version: "0.1"` в корневом); `log.md` — date-заголовки строго `## YYYY-MM-DD` (ISO 8601, **без скобок**).
3. **Ссылки — относительные/bundle-relative markdown** (`[t](x.md)`/`[t](/wiki/x.md)`). Битые ссылки в OKF допустимы, но мы их ловим lint'ом.

**Граница бандла (export profile, не «весь проект»).** Строгий OKF-бандл = `index.md` + `log.md` + `wiki/**`. `sources/`, `schema.md`, `.manifest.json` — **строительные леса, вне бандла**: это рабочий каталог скилла, а не conformant-дерево (сырьё в `sources/` без frontmatter сломало бы conformance, а добавлять его туда нельзя — сдвинет строки и порушит якоря). Поэтому «проект целиком» conformant-ом **не называть** — conformant именно экспорт этих трёх. Публикуешь строгий OKF — отдавай только их (и не линкуй из `index.md` на исключённый `schema.md`, иначе своя же lint поймает битую ссылку).

**Цитаты.** Наш блок «Источники» (`sources/<файл>.md:12-18`) — это диапазоны строк для слоя доверия; в OKF секция `# Citations` **опциональна**, так что блок оставляем как есть, к OKF-формату `[1] [Title](url)` не приводим. По желанию пользователя можно дополнительно отдавать `# Citations`, но это не требование conformance.

## Заглушка-перенаправление (redirect-stub)

После слияния дублей старый slug **не удаляется** (на него есть ссылки) — заменяется минимальной заглушкой. Контракт особый, **обычные leaf-инварианты (лид, «На этой странице», вербатим, «Источники») к ней не применяются** — lint не ругается:

```yaml
---
type: redirect
title: <старое имя>
redirect_to: <новый-slug>.md
---
Объединено с [<Новое имя>](<новый-slug>.md).
```

Дефолт — redirect-stub. Переписать все входящие ссылки и удалить старую страницу — **редкий эскалируемый вариант** (только с явного одобрения), не по умолчанию.

## Противоречия между источниками

Источники расходятся (книга X, статья Y) → **не выбирать победителя удалением.** Держать оба с якорями, явно показать расхождение (inline-блок «Расхождение» или отдельная страница для крупных), пометить тип:

- **эволюция / автор передумал** → новое основное, старое «пересмотрено»;
- **контекст-зависимость** → оба с условиями (часто не настоящее противоречие);
- **одно неверно / устарело** → пометить, предпочесть исправленное.

Спорное/неясное — **эскалировать пользователю**. История правок вики = git, её не вести.

## Стиль письма

- Нейтрально-профессиональный. Ассистент — **собеседник, не цитатник**: можно синтез, сравнение подходов.
- Спорное/устаревшее — отдельной секцией «Критика» / «Замечание», а не сглаживать.
- Английские термины — где естественны.
- Язык вики = язык источника.
- Не дублировать: перед созданием страницы искать существующую.

## Что НЕ делать

- Не редактировать `sources/`. Ошибку — поправкой на wiki-странице.
- Не пересказывать главу как страницу. Вики про концепты, не про хронологию.
- Не плодить дубли. Сначала поиск — потом создание.
- Не забывать обновлять `index.md` и `log.md` после изменений.
- Не вставлять в вику Claude-Code-специфичные конструкции — выход agent-agnostic.
- Не использовать Obsidian `[[ ]]` и не вставлять диаграммы — см. правило вверху файла.
